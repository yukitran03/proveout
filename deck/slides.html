ProveOut

Money moves when the work is proved, and anyone can prove it failed.

Job escrow on Creditcoin CC3 · settled by Attestcoin readability · no oracle operator, no arbiter

01
The problem

An AI agent working across chains cannot be paid safely.

Pay first and the buyer loses the money if the work never happens. Pay after and the agent has no guarantee it will ever be paid.

Every existing answer inserts a third party to decide whether the work was done: an oracle operator, an arbiter, or the platform itself. Someone, somewhere, presses a button.

02
The hole nobody names

Evidence that only the winner submits is not evidence.

The standard shape of a cross-chain settlement system is that the party who benefits watches for their own good news and submits it. A worker sees the repayment and posts it. A builder finishes the job and posts the receipt.

Nobody posts their own failure.

Such a system does not need to censor bad news. Bad news simply never arrives, because the only party watching has no reason to send it, and the escrow quietly waits out its timeout.

ProveOut pays strangers to submit it.

03
Architecture

Verification and payout in one Creditcoin transaction.

Ethereum Sepolia · source
WorkOracle.sol  reporter-gated ├ WorkCompleted(jobId, criteriaHash, │                builder, outputHash) └ WorkFailed(jobId, reason)
→
Creditcoin CC3 · settlement
SourceRegistry.sol └ emitter → chainKey, evmChainId,    topic0s, field positions JobEscrow.sol is ASCBase ├ execute(0) → release ├ execute(1) → challenge, any caller └ refund() after the deadline

A relayer waits for attestation, fetches the proof, and submits it. It is untrusted and anyone can be it: if it lies the contract rejects it, if it disappears anyone else can submit the same proof.

04
Attestcoin integration

The protocol's own entry point, not a wrapper around it.

  • JobEscrow inherits ASCBase and settles through the protocol's execute(). Replay protection and the query id are Attestcoin's, derived by the precompile from the verified Merkle path, not a caller-supplied transaction hash.
  • Block Prover precompile 0x0000000000000000000000000000000000000FD2, called with a continuity proof and a Merkle proof from the Proof Builder service. We build neither.
  • receiptStatus == 1 is mandatory. The precompile proves inclusion, not success.
  • EvmV1Decoder is imported from the published package, never copied in. A copy keeps compiling and starts decoding garbage the first time a field moves.
  • Two kinds of source, configurable. An attesting oracle whose event names the job, or any ordinary ERC-20, where the acceptance criterion is the Transfer itself. The second kind has no source-side trust assumption at all. Adding either is one registerSource call, not a code change.

05
The gate that matters

Inclusion is not success.

EvmV1Decoder.ReceiptFields memory receipt = ...;
if (receipt.receiptStatus != 1)
    revert ReceiptNotSuccessful(receipt.receiptStatus);

The precompile proves a transaction was included in a block. A reverted transaction is in the block too. Without this line a builder sends a completion call, lets it revert, proves that inclusion completely honestly, and is paid for work that never happened. Every proof in that attack is genuine.

This is the pattern Gluwa's own reference contract uses. We did not invent it. We refused to skip it.

06
Six gates on the settlement path
GateCheckWhat it stops
G1receiptStatus == 1a reverted call being paid as a success
G2emitter is registeredanyone deploying their own oracle and draining every escrow
G2bproved chain id matchesthe same bytecode redeployed on another attested chain
G3exact topic0 and topic counta different event settling a job
G4fields read from stored positionsindexed parameters read out of data as plausible garbage
G5query id unseenthe same proof settling twice
G6within the deadlinerelease and refund racing on transaction ordering

The challenge path reuses G1 to G5 and deliberately skips G6. A failure stays provable forever, or hiding one until the clock ran out would be a winning strategy.

08
Demo economics

The cost of being caught falls on whoever failed.

ParameterValue
Job payout1,000 tUSDC
Builder bond20% of the payout  ·  200 tUSDC
Challenger bounty50% of the bond  ·  100 tUSDC
On release, builder receives1,200 tUSDC  payout + bond returned
On challenge, buyer receives1,100 tUSDC
On challenge, challenger receives100 tUSDC  out of the builder's bond

The vault rule is balance + paidOut >= takenIn, an inequality rather than an equality, so a stranger sending one micro-unit into the vault cannot wedge every escrow in it.

09
Check it without trusting us

Anyone can verify a proof, with no wallet and nothing spent.

The precompile's verify is a view function, so the real verification path can be exercised against real attestation state for free.

IN THE BROWSER

proveout.vercel.app/verify

Paste any Sepolia transaction hash. It fetches a real Merkle and continuity proof, calls the precompile on Creditcoin, and shows the result with every log recovered from the proved bytes.

IN THE REPO

spikes/spike1_prove.ts

The same call from a terminal, unfunded. It is how the project's first gate was cleared before a line of contract code was written.

10
Boundaries

What this does NOT do.

  • Attestcoin proves inclusion, not exclusion. It can prove a transaction happened. It cannot prove none happened. ProveOut does not make hiding a failure impossible; it makes it detectable and expensive. That is the whole promise of the challenge mechanism, and not a word more.
  • An attested job trusts its oracle within its own scope. Whoever holds a reporter role decides what is provable there. A delivery job does not have this assumption, because the token is not ours and cannot be asked to lie. Choosing between them is a product decision.
  • TestUSDC is not USDC. A six decimal demo token with an open mint and no value.
  • Testnet only, and unaudited. Nothing here has had a security review.
  • The bond ratio is a demo parameter, not a modelled economic result.
  • Only transaction types 0 and 2 are accepted. Those are the two the shipped decoder fully decodes; anything else is rejected loudly rather than decoded on a guess.
  • The relayer is not trusted, but it is not yet redundant. Anyone can submit proofs; today only our worker does it automatically.
